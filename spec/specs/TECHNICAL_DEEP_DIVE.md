# Engineering deep dive: practical edge cases, system boundaries, exact contracts

## Layout and route state
The final experience may use a single shell and multiple nested route screens. Regardless of router strategy, deep links must express at least locale, floor, unit and room if appropriate. Visiting an unknown unit ID may redirect to floor selection with a nonblocking message. URL and local saved state must reconcile under deterministic precedence: explicit URL > approved persisted selection > app defaults. All values must be validated, and no route should crash when GLB hasn't loaded. UI should never render a unit for an amenity floor.

## Semantic architecture of scenes
Build a SceneRegistry keyed by sceneId and a FloorNodeIndex keyed by floorId. Each raycastable building level has a stable semantic ID, even if geometry optimized/instanced. Selection lights the correct floor or region and no other. Provide fallback DOM controls with exact same state transitions as 3D mesh clicks. When selected, highlight must remain noticeable in sunlight/dark scenes; use subtle edge/outlining, measured colors, no eye-searing neon. Scene focus target from predefined spatial metadata rather than naïve world origin. Balcony or interior hotspots should not be occluded by noninteractive transparent glass during raycasting; maintain separate hitbox layers.

## Precise camera behavior
Set camera min/max distance based on building bounding box and viewport aspect ratio. Use camera focus and orbit control ownership rules; only one system controls camera at a time. GSAP motion transitions can take ownership, abort old animation, and return to user control. Prevent jitter if mouse wheel scroll occurs while floor extraction animates. On restore/back, re-establish camera target and filtered pointer event handlers. Handle 90-degree screen orientation changes; target remains framed. Always offer Reset Camera with meaningful context (current scene bookmark rather than jump to default exterior). Add "Show Whole Floor" and "Look at selected room" actions that work even if pointer raycast selection failed.

## Three.js performance
Avoid allocating geometry, textures and materials on every frame and avoid React setState inside useFrame. Pool reusable material arrays; use mesh instancing for building repetitive facade components but not at cost of losing semantic floor selectable structure. Group static geometry into per-floor meshes for selection. Use LOD on furniture and facade small details; dynamic DPR and postprocessing only on high-performance devices; measure and tune rather than choosing aggressive fixed budgets. Favor shadow maps only for major key lights or baked shadows. Explicit sRGB output and toneMapping to approximate offline renders; HDR env exposure should be calibrated. When moving between multiple heavy scenes, ensure renderer textures/materials are correctly cached/disposed. Provide device-based selector quality and optional "Low graphics" toggle.

## glTF source-of-truth
Blender uses Z-up, Three/glTF often Y-up; exports need coordinate conversion and consistent unit scale. Keep object-level semantic identifiers in names or extras, not only fragile mesh ordering. Asset version hash changes invalidate stale indexes. In the build pipeline, glTF validator and scene manifest tests cross-check named surfaces, floor count, target bounding boxes and camera poses. Inspect materials converted from Blender Principled BSDF; know which nodes or procedural textures do NOT export. Bake complex procedural surfaces where necessary, with licensed texture sets and correct UV orientation. If using compression, bundle compatible decoders. Never ship dev-only 4K textures to every visitor; choose mipmaps and sensible resolution.

## Material swap implementation
A selectable surface is not identical to a material texture. A unit contains surfaces like living.floor.center, living.wall.north, living.panel.feature, kitchen.cabinet.fronts etc; each maps to one or more mesh nodes. Changing only the *selected surface* is default; "apply to whole apartment" must be explicit with a preview of changed slots. Avoid broad `.traverse()` replacing all materials named 'Floor' indiscriminately. Cache texture sets. For parquet/wood, rotate UV to follow realistic plank direction, true realistic board widths and visible seams; for tile show realistic 60x120 vs 60x60 look if size metadata claims so. Roughness and normal maps should visually distinguish stone, wood, painted plaster, not merely swatch hue. Avoid false physically measured properties.

## Form and data integrity
Use no real booking backend in fictional demo. A real-sales future integration may require admin login, CSRF protections, backend validation, anti-spam, email and GDPR/Iraqi privacy considerations; these are Phase 2 proposals. Client-side form accepts text only with robust length limits and avoids HTML injection. Consent required for local persistence if personal contact data, though better avoid storing contact data. Tests check intentionally malicious strings render harmlessly and do not execute. PDF documents contain chosen materials, issue time and fictional disclaimer. Any screenshot capture should crop out user identifying personal info.

## Arabic RTL implementation
Use semantic CSS logical properties; set `dir=rtl` for Arabic and preserve LTR isolated IDs (`U04A`, `125 m²`, `PDF`). Breadcrumb order, drawer origin, chevron direction, carousel swipe semantics, button icons and text alignment must be consistent, with Arabic numerals chosen deliberately. Font stack supports actual Arabic glyph shaping. Mixed Arabic/English room names preserve natural reading order. Input telephone numbers and emails remain LTR. Make sure numeric floor lists never visually reverse 01-11 ordering arbitrarily.

## Accessibility alternatives to canvas interactions
A Three Canvas is not semantically navigable by screenreader by default. Build an HTML list or accessible overlay matching all clickable floors, units and rooms. Keyboard actions and focus indicators are on DOM controls; camera may animate visually but selection state is not dependent on pointer. Visible labels show highlight and selection status in text. Every hot interaction can be achieved using DOM controls. Menus use `aria-expanded`, dialogs manage focus and Escape, status feedback is concise. Skip-to-content link and navigation landmarks appropriate. Reduced motion and "pause animated tour" required. Screenreader should receive a useful room/material description even if it cannot perceive the 3D scene.

## Render quality and web photo integrity
Each render may be a true Blender image with color grading, output metadata and camera angle, but still must clearly be labeled as conceptual render. User-selected materials may not match an earlier pre-render, requiring either correct paired package photo, true WebGL capture or explicit representative disclaimer. Technical metadata says `renderedPackageId`, `sourceSceneRevision`, `matchesActiveSelection:boolean`. If no match, the UI cannot show "Your final selected room" title. Capturing WebGL via preserveDrawingBuffer may hurt performance; choose safe screenshot pipeline and test browser contexts. Photo gallery should remain accessible if 3D renderer crashes.

## Fullscreen and mobile interactions
Phone users shouldn't accidentally pinch zoom webpage instead of scene or become stuck in orbit mode. Make interaction affordance and gesture instructions; use touch-action policy scoped to canvas, keep page scroll outside. Fullscreen gallery traps focus correctly, closes with X/back/Escape, and returns focus to launching thumbnail. Bottom drawers adapt to virtual keyboard and viewport safe areas. Landscape tablet image doesn't hide controls under nav bar. Quality toggles with data usage disclaimers (assets load lazily).

## Architectural consistency tests
Run checks: every floor elevation is monotonic; exactly 9 residential levels and 18 units; building facade level count matches data; unit room polygon boundaries don't overlap circulation illegally; balcony appears with proper exit from living; bedroom windows are placed in actual exterior walls; bath and kitchen plumbing shafts plausibly grouped; windows do not land inside columns; stair shafts align vertically; pool/wellness placement consistent across architecture and tour; dining roof line consistent in all renders.

## Operational maintenance and extensibility
Architectural sources must be editable. Provide tooling for updating a unit floorplan and regenerating 3D/proxy geometry plus camera/mesh metadata; document manual artist corrections when needed. Document material catalog import/export, image manifest update, translation keys and unit statuses. Avoid hardwired one-off U04A strings throughout UI; data-driven. Create a future migration plan for multi-project real estate CMS with company-level tenant isolation, proper auth and change logs, but do not implement unsafe fake admin authority in demo.

## Observability and incident handling
Centralized app-level errors and optional local debug panel in dev only; silence meaningless console spam. Failed GLB shows fallback/retry, not infinite spinner. Interaction loading state surfaced, e.g. "Loading apartment interior". Error reports do not expose personal data or secrets. If an asset format unsupported, select appropriate fallback; if KTX2 shader decode fails, offer plain WebP variant or conservative material; avoid blank screen. Show tested browser/GPU details in delivery report.

## Visual fidelity escalation plan
If exterior currently looks generic, address geometry massing + window proportions before adding fancy shaders. If materials look plastic, fix PBR maps/roughness/sRGB/exposure. If rooms look fake, fix geometry scale/furniture/window/light/shadow. If visual output resembles a PowerPoint slideshow, restore spatial navigation and continuous 3D controls. If 3D is too slow, hybrid should preserve meaningful spatial selection/live material swapping while precalculating hero photos. Prioritize aesthetic deficits that influence a company's first 30 seconds, without losing core functionality.
